## OBJECTIVE

Determine whether current IABV can already compose its existing organs into a general experimental loop that learns how an unfamiliar environment is structured, rather than requiring provider-specific rules for every application, browser, operating system or device.

The target is not more browser automation. The target is a transferable reasoning algorithm:
objective → uncertainty → observe → normalize → identify concepts/entities → hypothesize relations/states → select discriminating experiment → choose capability-fit actor/resource → governed action → observe transition → independent verification → update semantic knowledge → derive capability → decision → outcome → reusable knowledge.

Treat the laptop/device, operating system, browser, applications, files, processes, network, accounts, sessions, credentials and access channels as one connected environment. Also model the human and external AIs as heterogeneous evidence/action resources with different authority, independence, cost and capabilities.

## HUMAN + EXTERNAL AI AS EXPERIMENTAL RESOURCES

Audit whether the existing architecture can use:
- human: objective clarification, semantic disambiguation, ground truth, explicit authorization;
- external AI: independent interpretation, implementation, execution, critique or verification;
- IABV-native organs: observation, self-model, discernment, experiment selection and learning;
- browser/API/CLI/MCP: concrete observation/action channels.

The question is not whether all actors are equal. The question is whether IABV can select the actor/channel that most reduces the current uncertainty under governance.

## BROWSER AS LABORATORY

Determine whether current browser infrastructure can support a controlled experiment on an unfamiliar web application without any provider-specific semantic class.

The semantic behavior under test should be something like:
observe page
→ infer authentication-flow candidate
→ identify identifier field candidate
→ identify secret field candidate
→ identify submit operation candidate
→ hypothesize authentication-required state
→ perform one explicitly authorized transition
→ observe before/after
→ distinguish authenticated session from permanent account identity
→ infer resulting capability
→ verify with an independent observation source where possible.

The implementation may use DOM, accessibility, CDP, Playwright or OS-specific drivers. Those are adapters. The semantic algorithm must not depend on a specific provider name or selector.

## GENERALIZATION TEST

Design the smallest experiment that can be repeated on TWO materially different applications or page structures.

One case should be able to produce a false or ambiguous login-like signal. Example: a public form containing an email field but no authentication transition.

The system must be able to preserve uncertainty rather than force a positive classification.

Success is not 'the page was automated'. Success is that the same reasoning mechanism interprets materially different environments using observations and controlled transitions.

## SMALLEST DISCRIMINATING EXPERIMENT

After the forensic map, design ONE minimal experiment that distinguishes the leading architectural hypotheses.

It must:
- use existing organs first;
- avoid creating a universal ontology or new central brain;
- avoid provider-specific semantic classes;
- have a positive case and at least one negative/ambiguous case;
- preserve before/after state;
- preserve evidence provenance;
- specify what would count as observed, inferred, verified and effective;
- identify who/what executes it;
- identify the independent verifier;
- identify exactly what decision would change if the experiment succeeds.

Do not implement this experiment. Only define it so the next actor can execute it.

## STRICT STOP RULES

Stop and report instead of designing implementation if:
- the claimed capability already exists and only lacks verification;
- another existing organ already owns the proposed responsibility;
- the experiment would require a new central coordinator without proving a semantic gap;
- provider-specific logic would be introduced into the universal layer;
- a runtime mutation would contaminate a supposedly observational audit;
- the only way to prove the claim is to assume the relation beforehand.
