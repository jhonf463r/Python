- `285-A08`: asterisk wildcard.

- `285-A12`: repeated separator producing an empty component.
- `285-A13`: component ending in a dot.
- `285-A14`: component ending in a space.
- `285-A15`: tilde/short-name pattern.

- `285-A30`: a valid path of exactly 240 ASCII characters is accepted.
- `285-A31`: a valid path with exactly 16 components is accepted.
- `285-A32`: a valid component at the permitted maximum length is accepted.

Add one-over-the-limit negative controls for component length, total path length, and component count. These positive cases are mandatory so a deny-all validator cannot pass.

### 1.3 Crash-point enum and expected recovery

The `crash_point` enum is exactly:
`NOT_APPLICABLE`, `BEFORE_INTENT_COMMIT`, `DURING_INTENT_COMMIT`, `AFTER_INTENT_COMMIT_BEFORE_OPEN`, `AFTER_OPEN_BEFORE_READ`, `DURING_READ_BEFORE_STAGE_COMMIT`, `AFTER_CONTENT_STAGED_BEFORE_FINAL_GATE`, `DURING_FINAL_GATE_BEFORE_RELEASE_AUTHORIZED`, `AFTER_RELEASE_AUTHORIZED_BEFORE_HANDOFF`, `DURING_HANDOFF`, `AFTER_HANDOFF_RETURN_BEFORE_HANDOFF_COMMIT`, `AFTER_TRUSTED_ACK_RECEIVED_BEFORE_ACK_COMMIT`, `AFTER_ACK_AND_DELIVERED_ATOMIC_COMMIT`.

Each crash fixture forces one crash point with all other conditions held constant:
1. **Before/during intent commit:** the atomic transaction yields either no operation/intent and no content I/O, or a complete committed intent and reservation. A partial key, operation ID, or reservation is `LEDGER_INTEGRITY_UNPROVEN`. Recovery must inspect durable authoritative state before reads resume.
2. **After intent commit but before open; after open but before read; or during read before a durable stage record:** lifecycle `UNRESOLVED`; reader halted; maximum reservation retained; no content released.
3. **After durable `CONTENT_STAGED` but before final gate; or during final gate before durable `RELEASE_AUTHORIZED`:** recovery cannot deliver staged content. The operation stays/returns `UNRESOLVED` pending authenticated reconciliation; reservation remains charged; reader halts; inaccessible staged material is destroyed where safely supported. Do not claim terminal `DISCARDED` until the discard and its durable record are complete.
4. **After durable `RELEASE_AUTHORIZED` but before handoff; during handoff; or after local handoff returns but before `HANDOFF_RETURNED` commits:** actual external delivery is uncertain. Recover as `UNRESOLVED`, retain maximum reservation, halt reads, and never automatically replay.
5. **After trusted acknowledgement arrives but before the acknowledgement/DELIVERED transaction commits:** recovery is `UNRESOLVED`; a volatile receipt is not delivery proof; do not redeliver.
6. **After the acknowledgement and `DELIVERED` commit atomically:** recover persisted `DELIVERED`, with no second handoff, content redelivery, intent, or reservation.

If durable state cannot establish the intent transaction's outcome, do not infer `NONE` from lost process memory. Use `LEDGER_UNAVAILABLE` or `LEDGER_INTEGRITY_UNPROVEN` according to evidence and keep the reader fail-closed. Every crash point above has its own fixed fixture and traceability.

## 2. S9 — Trusted delivery acknowledgement and crash recovery

### 2.1 Acknowledgement capability and evidence binding

Add `transport_ack_capability` with exactly two values:
- `NONE` — transport has no verifiable recipient acknowledgement outside requester control.
- `TRUSTED` — a recipient-side service/transport authority is authenticated under protected configuration and the requesting agent cannot create, alter, suppress, or replay its acknowledgement evidence.

A trusted acknowledgement cannot be a requester boolean, caller-supplied token, local log, echoed operation ID, or ordinary HTTP/client call return. It must bind:
- server-generated `operation_id`;
- server-configured recipient identity and destination/provider digest;
- unique handoff/correlation ID;
- versioned canonical response digest over the exact payload bytes or deterministically serialized list names handed off;
- response type and byte/entry count;
- unique acknowledgement event ID/nonce and trusted event time;
- authenticated acknowledgement authority identity and trust/key version.

The ledger receipt contains no repository content. The destination and recipient are retrieved from protected server configuration and must match the approved scope; the requester cannot select or change the ack authority during the operation.

### 2.2 One lifecycle transition rule

For the next consolidated schema, `DELIVERY_ACKNOWLEDGED` is an audit event, not a persisted `expected_lifecycle_state` value. Remove it from the lifecycle enum and use a separate field `expected_delivery_ack_status`. `DELIVERED` remains the terminal lifecycle value after a trusted ack. This expressly supersedes inherited wording that could treat acknowledgement and delivered as interchangeable states.

The `expected_delivery_ack_status` enum is:
`NOT_APPLICABLE`, `NO_ACK_REQUIRED`, `WAITING`, `ACK_ACCEPTED`, `ACK_INVALID`, `ACK_MISMATCH`, `ACK_REPLAYED`, `ACK_TIMED_OUT`, `ACK_SOURCE_UNAVAILABLE`, `ACK_COMMIT_FAILED`.

Normative transition:
1. All final gates must pass and `RELEASE_AUTHORIZED` must be durable before any content handoff.
2. When the local handoff call returns, commit `HANDOFF_RETURNED` durably. This proves only that the local handoff API returned, not that the recipient received the payload.
3. In mode `NONE`, `HANDOFF_RETURNED` is the strongest terminal claim and `expected_delivery_ack_status=NO_ACK_REQUIRED`. Never claim `DELIVERED`.
4. In mode `TRUSTED`, lifecycle stays `HANDOFF_RETURNED` while awaiting the authenticated ack. Status is represented in `expected_delivery_ack_status`. The proposed maximum ack interval is 30 seconds from trusted handoff-return time, controlled by server configuration and never requester-extendable.
5. A valid, unexpired acknowledgement is committed in one atomic durable transaction that records the acknowledgement event/evidence and transitions lifecycle to `DELIVERED`. The transaction commits both or neither. There is no separate durable lifecycle state `DELIVERY_ACKNOWLEDGED`.
6. If the ack is missing at deadline, the authority is unavailable, proof is invalid, operation/recipient/digest does not match, the event ID is replayed, or the ack/DELIVERED transaction cannot be durably committed, delivery cannot be claimed. Record `UNRESOLVED` when possible, keep the reader halted for new content-bearing operations, retain the reservation, and require authenticated Owner/governance reconciliation. Never automatically replay a possibly delivered response.
7. A requester-supplied or otherwise untrusted fake ack is ignored as delivery evidence and audited. It does not trigger a request-controlled global halt. Failures of the authoritative ledger/ack recovery record follow the higher-priority ledger rule.

If a trusted ack arrives before `HANDOFF_RETURNED` is durable, it cannot authorize or prove delivery on its own. A crash before the operation's handoff/ack evidence is durably committed recovers conservatively as `UNRESOLVED`; never replay.

### 2.3 Required recovery cases for both modes

Create independent fixtures for every case:
- Mode `NONE` crash before `RELEASE_AUTHORIZED`: recover the last durable state; no delivery.
- Mode `NONE` crash after `RELEASE_AUTHORIZED` but before durable `HANDOFF_RETURNED`: `UNRESOLVED`, halt, no replay.
- Mode `NONE` crash during handoff or after return but before `HANDOFF_RETURNED` commit: `UNRESOLVED`, halt, no replay.
- Mode `NONE` crash after durable `HANDOFF_RETURNED`: return that state with `NO_ACK_REQUIRED`; do not claim `DELIVERED` or replay.
- Mode `TRUSTED` crash before `RELEASE_AUTHORIZED`: recover last durable state; no delivery.
- Mode `TRUSTED` crash after `RELEASE_AUTHORIZED` but before durable `HANDOFF_RETURNED`: `UNRESOLVED`, halt, no replay.
- Mode `TRUSTED` crash during handoff or before the handoff-return commit: `UNRESOLVED`, halt, no replay.
- Mode `TRUSTED` with durable `HANDOFF_RETURNED` and ack deadline open: status observer may see `WAITING`; no delivery claim, content redelivery, new intent, or reservation.
- Valid ack received but crash before atomic ack/DELIVERED commit: `UNRESOLVED`, halt, no replay.
- Valid ack and `DELIVERED` atomically committed before crash: return persisted `DELIVERED` and `ACK_ACCEPTED`; never repeat handoff.
- Trusted ack deadline expires without a durable valid ack: `UNRESOLVED` / `ACK_TIMED_OUT`, halt, no replay.
- Required ack source/record unavailable: `UNRESOLVED` / `ACK_SOURCE_UNAVAILABLE` unless a higher-priority ledger availability/integrity result controls.

### 2.4 Acknowledgement validation fixtures

Separate tests must establish:
- valid ack binds exact operation, configured recipient, response digest/count, handoff ID, and event ID → atomic ack evidence plus `DELIVERED`;
- repeated event ID → `ACK_REPLAYED`, no second delivery event/state transition;
- wrong recipient → `ACK_MISMATCH`, no delivery claim;
- correct operation/recipient but wrong response digest or count → `ACK_MISMATCH`;
- requester-fabricated success ack → not trusted; no change to delivery status;
- valid ack and atomic commit at `Tack−1ms` → accepted;
- ack commit exactly at `Tack` or later → `ACK_TIMED_OUT` and unresolved recovery;
- query after committed `DELIVERED` → status only, no content, intent, reservation, or redelivery;
- mode `NONE` plus durable `HANDOFF_RETURNED` → no delivery claim.

### 3.2 Phase-aware precedence and required pairs

An earlier phase stops later phases; a later-phase gate cannot be inferred or evaluated if an earlier phase failed. The next consolidated R2 table must have one `phase` value for every gate and explicit precedence fixture coverage.

Mandatory applicable pairs:

- Ledger integrity failure plus prior unresolved operation → `LEDGER_INTEGRITY_UNPROVEN` as the earlier R2 selection; no operation status from an untrusted ledger.
- Prior `UNRESOLVED` with registry rollback also reported → `UNRESOLVED` under Entry 280's order.
- `REGISTRY_ROLLBACK` plus `DECISION_NOT_APPLICABLE` → `REGISTRY_ROLLBACK`.
- `DECISION_NOT_APPLICABLE` plus `APPROVAL_CHANNEL_UNTRUSTED`, when both are eligible in the same preflight → `DECISION_NOT_APPLICABLE`.
- `APPROVAL_CHANNEL_UNTRUSTED` plus `PATH_FORM_UNSUPPORTED`, when both are eligible in the same operation preflight → `APPROVAL_CHANNEL_UNTRUSTED` under the inherited R2 order. Path validation still occurs before any filesystem lookup.
- Unsupported path syntax plus any would-be path-scope/object lookup result → `PATH_FORM_UNSUPPORTED` and no filesystem lookup; the later lookup condition is not observed.
- `BLOCK_SCOPE_UNEVALUABLE` plus `BLOCK_RELEASE_UNSUPPORTED` → `BLOCK_SCOPE_UNEVALUABLE`.
- `BLOCK_RELEASE_UNSUPPORTED` plus `DECISION_EXPIRED` when both are safely established in the same preflight → `BLOCK_RELEASE_UNSUPPORTED` under R2.
- `DECISION_EXPIRED` plus `DECISION_REVOKED` when both are independently established in the same eligible final gate → `DECISION_EXPIRED`; staged content is discarded.
- `DECISION_REVOKED` plus `REVOCATION_UNAVAILABLE` from a single authoritative query is inapplicable by invariant unless the authenticated source protocol explicitly represents both facts. The next consolidated contract must either define that protocol and a winner or mark the pair `INAPPLICABLE_BY_INVARIANT` with proof; it cannot omit the pair silently.
- `BUDGET_EXCEEDED` plus a would-be post-open `CONTAINMENT_UNPROVEN` → `BUDGET_EXCEEDED` in the reservation phase; do not open/read the object to discover containment.
- `BUDGET_EXCEEDED` plus file/list overflow → `BUDGET_EXCEEDED`; no content I/O or cap probe occurs.
- Final-gate `DECISION_REVOKED` plus `FILE_LIMIT_EXCEEDED` after a bounded file read → `DECISION_REVOKED`; public `REQUEST_DENIED`; lifecycle `DISCARDED` if bytes were staged; no content release.
- Final-gate `DECISION_REVOKED` plus count-first list overflow on a safely bound stable directory → `DECISION_REVOKED`; public `REQUEST_DENIED`; lifecycle `DENIED` because no names were staged; no content release.
- Final-gate `DECISION_EXPIRED` plus `FILE_LIMIT_EXCEEDED` after bytes are staged → `DECISION_EXPIRED`; lifecycle `DISCARDED`; no content release.
- At the final gate, if `CONTAINMENT_UNPROVEN` and a lower-priority revocation/limit result are both actually observed, select by R2 order among those same-phase observations; staged content is discarded. If containment failed before open and therefore prevented the later observations, do not fabricate a dual-failure fixture.

For every adjacent gate pair, the manifest must either include a discriminating case with one winner or mark the pair `INAPPLICABLE_BY_PHASE` / `INAPPLICABLE_BY_INVARIANT` and identify the exact phase/invariant. “Not tested” is not a permissible status. All phase assignments must agree with Entry 280's priority order plus Entry 284's atomic reservation/open/final-gate ordering.

### 3.3 Required temporal boundary matrix

For every relevant deadline, include three independent fixtures at `T−1ms`, exactly `T`, and `T+1ms` under a deterministic injected clock with declared resolution. For a strict deadline, only `now < deadline` is valid; equality is expired.

Required deadlines:
- Challenge nonce TTL, no later than 120 seconds after challenge creation.
- Owner-attestation freshness, proposed maximum 60 seconds; test issuance-start and durable-commit time separately.
- Fixed public window, `Dwindow=T0+120s`. Before it, the original accepted request gets `APPROVAL_PENDING`. At the endpoint, issue `DECISION_ISSUED` only if an eligible hidden decision was durably committed before all issuance deadlines; otherwise `REQUEST_UNAVAILABLE`.
- Hidden-decision lifetime, proposed maximum five minutes from `not_before=Dwindow`. At exact expiry the decision is expired.
- Revocation proof freshness. The server configuration must define a finite protected `revocation_freshness_ttl` and authenticated proof time/version. Test proof age at TTL−1ms, TTL, TTL+1ms. Missing TTL, unavailable source, stale proof, and missing/unauthenticated proof are separate fixtures yielding `REVOCATION_UNAVAILABLE` unless a higher-priority R2 condition applies.
- Wall/monotonic clock disagreement and suspend semantics from Entry 278 C3-08: discrepancy below and exactly 2,000 ms does not expire solely on the tolerance; greater than 2,000 ms expires the decision; unknown suspend semantics expire active decisions/nonces; any detected backward wall-clock step expires active decisions/nonces. Use separate fixtures.
- Trusted acknowledgement deadline `Tack` from §2.2: test Tack−1ms, Tack, Tack+1ms. The acknowledgement/DELIVERED commit must linearize strictly before Tack.

Every time fixture specifies which deadline controls and the exact requester/internal/lifecycle result. The proposed acknowledgement TTL and any revocation freshness TTL remain `PROPOSED` until accepted in a consolidated contract; the revocation TTL may not be omitted or supplied by the requester.

### 3.4 Final-gate revocation with staged content

Include a single-fault final-gate fixture where a valid operation committed intent/reservation, staged its bounded result, and then the authoritative revocation source supplies a fresh authenticated revocation fact before release.

Expected: internal `DECISION_REVOKED`; public `REQUEST_DENIED`; lifecycle `DISCARDED`; reservation retained with no refund; no content release; durable denial/completion record committed. If that commit fails, recover `UNRESOLVED` and halt. Never redeliver.

Add a separate case where the source is unavailable/stale rather than proving revocation. Expected internal `REVOCATION_UNAVAILABLE` and no content release. Do not combine these scenarios.

### 3.5 Positive controls that defeat deny-all

The next manifest must contain valid end-to-end positive controls:
- An explicitly allowlisted, non-sensitive in-scope file read where the Owner approval is fresh; target binding and containment are sound; no unreleased block applies; epochs are current; revocation proof is fresh; ledger is available; decision is unexpired; and the aggregate reservation commits.
- An exact-at-cap file read that completes without overflow.
- A non-recursive listing of exactly 200 actual valid entries with stable enumeration and no unsafe entries.
- A status query of a valid completed operation that returns status without delivering content again.
- Mode `NONE` with a valid handoff returning `HANDOFF_RETURNED`, without a `DELIVERED` claim.
- Mode `TRUSTED` with a valid recipient-bound acknowledgement atomically committed with `DELIVERED`.

These positives do not bypass fresh Owner approval, sensitive-path denial, independent block release where required, or final-gate checks. A deny-all mutant must fail. If the contract cannot state a supported positive authorized path, that remains a blocker rather than grounds to weaken controls.
