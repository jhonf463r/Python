## DURABLE KNOWLEDGE DELTA

### 1. Capability is not one vocabulary

IABV currently contains multiple capability representations:

- required/readiness IDs;
- `EnvironmentCapability`;
- `ToolCard.capabilities`;
- `AssistantStrength`;
- task kinds / routing aliases;
- StrategyPack.required_capabilities.

These are not yet proven to form one coherent semantic contract.

Therefore preserve:
`same concept ≠ same identifier ≠ same contract`.

A similarity of names does not establish a bridge.

### 2. Demand and supply must remain separated

The correct conceptual separation is:

`OBJECTIVE / INTENT → REQUIRED CAPABILITY`
`WORLD / ENVIRONMENT / RESOURCE STATE → READINESS / AVAILABILITY / FEASIBILITY`
then:
`REQUIRED CAPABILITY + VIABLE REALIZATIONS → GOVERNED ROUTING`.

Do not make environmental state arbitrarily redefine the user's need. Environmental evidence should primarily constrain, qualify, or reshape realization/readiness unless a separate, proven interpretation mechanism exists.

### 3. The present universal problem is representational composition, not absence of organs

Existing organs include:
`CapabilityReadinessService`,
`StrategyPackRegistry`,
`ToolRegistry/ToolCards`,
`EnvironmentSelfAwarenessService`,
`WorldModelService`,
`AssistantCapabilityRegistry`,
`SynapticRouter`,
and the normal adaptive orchestrator.

Current evidence does NOT justify a new universal capability brain/registry/core.

Construction order remains:
`REUSE > COMPOSE > WIRE/REPAIR > EXTEND > NEW`.

This is static source-level evidence. Runtime route impact is not yet proven.

## DEVELOPMENTAL / PLASTICITY DELTA

Treat IABV's desired neuroplasticity as an engineering hypothesis operationalized through observable mechanisms, not as a claim that software has biological neuroplasticity.

Desired developmental property:

`experience / observation`
→ `verified reusable capability knowledge`
→ `composition / generalization / refinement`
→ `context-conditioned activation`
→ `later non-identical reuse`
→ `changed future decision or implementation`.

Preserve the broad repertoire:

`capability inventory ≠ active capability set`
`selection ≠ deletion`
`unavailable now ≠ useless generally`.

A successful developmental change may:
`ACQUIRE | REFINE | COMPOSE | CONSOLIDATE | SPECIALIZE | GENERALIZE | SUPERSEDE | ROLLBACK`.

The universal objective is not to preprogram every application, operating system, tool or task. It is to make the system increasingly able to discover, represent, compose, verify and reuse capabilities across realizations.
