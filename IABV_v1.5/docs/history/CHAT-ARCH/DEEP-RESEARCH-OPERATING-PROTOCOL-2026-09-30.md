# IABV v1.5 — DEEP RESEARCH OPERATING PROTOCOL
## Research Through ChatGPT — 2026-09-30

## PURPOSE

Define how IABV must invoke, observe, adjudicate and learn from external Deep Research executions.

Deep Research is a **capability/resource**, not an epistemic authority over IABV.

The central risk demonstrated by the 2026-09-30 research cycle is not lack of report-generation ability. It is semantic substitution at the task/execution boundary.

---

# 1. CORE MODEL

Never model:

`prompt → report`

Use:

`objective → research contract → execution instance → input/object verification → bounded research → result-signature validation → source/evidence adjudication → accepted knowledge → IABV reconciliation`.

---

# 2. REQUIRED SEPARATION OF ROLES

Every invocation has two distinct layers:

### A. TASK SPECIFICATION
What the external researcher is instructed to do.

### B. RESEARCH OBJECT
The phenomenon/questions the researcher must investigate.

The task specification is NOT automatically the research object.

An attachment, filename, phase label, or prompt title is NOT automatically the research object.

Examples established by the 2026-09-30 failures:

`Phase 2A label ≠ software specification`

`attached prompt ≠ object to audit`

`"deep research" ≠ topic "how to research"`

`missing input ≠ generic replacement task`.

---

# 3. RESEARCH INVOCATION CONTRACT

Before launching Deep Research, IABV must create a unique execution identity containing:

- EXECUTION_ID;
- OBJECT_ID;
- RESEARCH_PHASE;
- EXACT_RESEARCH_OBJECT;
- CENTRAL_QUESTION;
- IN_SCOPE;
- OUT_OF_SCOPE;
- REQUIRED_RESULT_SIGNATURE;
- STOP_CONDITIONS;
- INPUT_PROVENANCE;
- OPTIONAL_CONTEXT_SOURCES;
- ACTOR/CAPABILITY FIT.

The execution identity must be distinct from the research object.

A repeated diagnostic token must never be reused as the sole identity of a new research execution.

---

# 4. CONTEXT SOURCE RULE

Repository/GitHub context may be used when it materially improves grounding, but it must be typed:

`IABV-CONTEXT`

External scientific literature must be typed:

`EXTERNAL-SCIENCE`

Researcher synthesis:

`RESEARCHER-SYNTHESIS`

Unresolved:

`UNRESOLVED`

Rules:

`IABV-CONTEXT ≠ scientific evidence`

`scientific paper ≠ proof of IABV implementation`

Repository access is useful for Stage B reconciliation but must not be a hidden prerequisite for understanding a self-contained external research object.

---

# 5. FAIL-CLOSED INPUT BEHAVIOR

If an attachment, repository file or external source is unavailable:

1. preserve the exact research object already defined in the execution contract;
2. do not invent or reconstruct missing contents;
3. do not substitute a generic task;
4. state the exact missing dependency if it blocks a claim;
5. continue only with evidence that is actually available.

Therefore:

`missing input → fail closed`

not:

`missing input → generic completion`.

---

# 6. TWO-STAGE RESEARCH FOR IABV SCIENCE

### STAGE A — EXTERNAL SCIENCE

Investigate the external scientific literature only.

Allowed:
- definitions;
- mechanisms;
- empirical findings;
- benchmarks;
- experimental designs;
- false-positive controls;
- causal evidence;
- metacognition;
- learning/plasticity;
- knowledge revision;
- relation reorganization;
- self-modeling;
- autonomous experimentation;
- consciousness indicators.

Forbidden:
- current IABV architecture reconstruction;
- invented IABV components;
- generic security audit;
- generic requirements engineering;
- generic software architecture;
- implementation roadmap.

### STAGE B — IABV RECONCILIATION

Only after Stage A passes acceptance:

`scientific construct → IABV organ/path → source evidence → runtime evidence → state classification → causal frontier`.

---

# 7. OBJECT-TARGET GATE

The first adjudication question is:

**What did the researcher actually investigate?**

Compare the answer literally with the canonical research object.

Reject when the primary object becomes:
- the research methodology itself;
- the Deep Research tool;
- the attached prompt/specification;
- generic requirements engineering;
- generic architecture;
- cybersecurity;
- project management;
- another neighboring domain.

A long, well-cited, internally coherent report about the wrong object remains rejected.

---

# 8. RESULT GATES — ORDER MATTERS

Evaluate in this exact order:

`OBJECT ALIGNMENT`
→ `REQUIRED COVERAGE`
→ `SOURCE SUPPORT`
→ `EVIDENCE QUALITY`
→ `METHODOLOGICAL RIGOR`
→ `SYNTHESIS QUALITY`.

Do not allow report length, citation count, technical vocabulary, diagrams, tables or roadmap completeness to substitute for earlier gates.

---

# 9. DIAGNOSTIC VS RESEARCH EXECUTION

Diagnostics are allowed only to answer a specific discriminating interface question.

Example:

`OBJECT ECHO DIAGNOSTIC`

tests object preservation.

It does NOT produce the requested scientific knowledge.

Once a diagnostic has passed for the relevant property, do not repeatedly relaunch it.

Repeated return of the same diagnostic structure is evidence of:

`diagnostic replay / execution-handoff ambiguity`

until proven otherwise.

---

# 10. EXECUTION-PROVENANCE REQUIREMENT

For every result, preserve separately:

`requested prompt`

`prompt actually submitted, if observable`

`execution instance`

`result returned`

`independent adjudication`.

Never infer:

`canonical prompt exists → canonical prompt was executed`.

This distinction is mandatory.

---

# 11. SCIENTIFIC EVIDENCE CONTRACT

For research on IABV's developmental/scientific objective, require explicit discrimination of:

`adaptation`
→ `reusable learning`
→ `knowledge/belief revision`
→ `contextual specialization`
→ `relation reorganization`
→ `causal learning`
→ `metacognitive control`
→ `self-modeling`
→ `self-directed experimentation`
→ `future-decision influence`.

Use the delta model:

`ΔW / ΔM / ΔK / ΔR / ΔC / ΔD / ΔB / ΔO`

and false-positive controls.

---

# 12. WHEN TO CHANGE ACTOR

Do not change actor merely because one research result is bad.

Change actor only when the evidence supports an actor/capability bottleneck, for example:

1. exact execution input is independently established;
2. object is preserved or task interface is known to be correct;
3. required source access is available;
4. the actor repeatedly fails the same critical capability;
5. a different actor has demonstrated a capability better matched to the observed bottleneck.

Actor selection therefore remains frontier-driven:

`current truth → uncertainty → required capability → capability-fit actor`.

---

# 13. KNOWLEDGE ABSORPTION

Do not absorb the result directly.

Use:

`result → object gate → source audit → claim/evidence classification → contradiction analysis → Knowledge Delta`.

Distinguish:

`report`
`artifact`
`source`
`evidence`
`interpretation`
`verified knowledge`.

---

# 14. 2026-09-30 LEARNING FROM THE FAILURE SERIES

The observed sequence produced the following negative knowledge:

1. Phase-1 consciousness overview:
   partially valid but insufficient for IABV's full scientific objective.

2. Security report:
   topic drift.

3. Security + invented architecture:
   topic drift + document-centric drift + unsupported IABV reconstruction.

4. Security + generic metrics/architecture:
   template-driven completion + false specificity.

5. Generic "what is deep research":
   meta-research drift.

6. Requirements/SRS report:
   missing-input fallback + generic substitution.

7. Phase-2.1 requirements report:
   document-centric drift recursion.

8. Object-echo diagnostic:
   object preservation provisionally demonstrated, repository ingestion not demonstrated.

9. Repeated object-echo output:
   diagnostic replay / execution-handoff ambiguity.

The durable interpretation is:

`not all failures are actor failures`.

They must be separated into:

`object failure`
`input/delivery failure`
`execution-selection failure`
`source-access failure`
`research capability failure`
`result-quality failure`.

---

# 16. DEFAULT HUMAN/AI HANDOFF FORMAT

Every future Deep Research request should make it possible to answer:

**What exactly was asked?**

**What exactly was executed?**

**What exactly was researched?**

**What sources support it?**

**What did not get established?**

**What knowledge changed?**

**What remains open?**

These are separate questions and must remain separate in the record.

## 2026-09-30 PARALLEL-TRACK RULE — SCIENCE VS REAL SELF-DEVELOPMENT

La pista científica de Deep Research y la pista técnica de IABV self-development son independientes.

### SCIENCE TRACK
`Deep Research → scientific result → source/evidence adjudication → IABV Stage B`

Purpose: establish external scientific evidence for learning, revision, relation reorganization, metacontrol, self-directed experimentation and higher-order developmental hypotheses.

### ENGINEERING/RUNTIME TRACK
`IABV self-observation → required capability → actor/resource selection → real Devin execution → observation → independent verification → writeback → changed next action`

Purpose: establish that IABV can actually participate in its own development through the existing control-plane mechanisms.

Do not make the science track a prerequisite for the first real IABV→Devin runtime test.
Do not use a successful runtime consultation as proof of the scientific developmental hypotheses.
Treat both tracks as evidence-producing tracks that later converge through reconciliation.
