## 1. C16-S1 — Make the acknowledgement classifier conditions disjoint and preserve pre-deadline failure

### 1.1 Normative status classifier

For trusted-ack operations, `expected_delivery_ack_status` describes the currently observed acknowledgement event/transaction status; `expected_internal_code` independently describes the selected internal/recovery result. Never encode `LEDGER_UNAVAILABLE` or `LEDGER_INTEGRITY_UNPROVEN` into the acknowledgement-status enum.

Use the coordinator's protected monotonic timebase. Define `Tack = Thandoff + 30s`, where `Thandoff` is the durable `HANDOFF_RETURNED` transition time. `ack_received_at` is stamped at the trusted ingress only after authentication and exact binding to operation, handoff ID, configured recipient, response digest/count, authority, and event ID. It and `Tack` must use the same protected monotonic domain. A remote authority wall-clock timestamp is audit metadata only and cannot replace the trusted local ingress timestamp.

For a valid receipt and its unique operation-bound commit slot, evaluate the following rules in order; the first satisfied rule wins:

1. **`ACK_TIMED_OUT` from independently sufficient deadline evidence.** Select this status if (a) a valid authenticated local receipt has `ack_received_at >= Tack`; or (b) the complete authoritative journal records the one allowed commit attempt as rejected by the strict deadline predicate at or after `Tack`; or (c) no valid receipt was received by `Tack`, trusted evaluation is at/after `Tack`, and the acknowledgement authority's ingress watermark plus the complete transaction outcome index positively establish that no valid receipt/commit existed by the deadline. Case (c) is unavailable when a valid pre-deadline receipt exists, even if no commit occurred. A proven late receipt remains `ACK_TIMED_OUT` if the commit-outcome source later becomes unavailable.
2. **`ACK_ACCEPTED`.** Select only when a valid authenticated receipt timestamp satisfies `ack_received_at < trusted_commit_time < Tack`, the authoritative ledger proves that the acknowledgement evidence and `DELIVERED` lifecycle were committed atomically and durably, the receipt/commit timestamp relation is valid in the common protected time domain, and the applicable attempt journal and transaction index support that result.
3. **`ACK_COMMIT_FAILED`.** Select when a valid authenticated receipt has `ack_received_at < Tack`; the sole operation/handoff commit slot has been consumed; authoritative, recovery-closed evidence proves no acknowledgement/`DELIVERED` success committed and no commit remains in flight; and the registered attempt was rolled back, aborted, interrupted, or closed by recovery as `RECOVERY_ABORTED_NO_COMMIT`. There must be no `REJECTED_DEADLINE` outcome or other independently sufficient deadline-timeout evidence for that attempt. The status does not change merely because the recovery/query time is after `Tack`.
4. **`WAITING`.** Select when trusted evaluation is strictly before `Tack`; no durable success exists; no attempt has rolled back, failed, been aborted, or been interrupted; and the authenticated checkpoint/journal is current and available. There may be no receipt yet, or a valid pre-deadline receipt may exist while the unique commit attempt is explicitly `IN_PROGRESS` and its writer remains live. A live in-progress attempt is a valid waiting state, not a complete recovery closure.
5. **`ACK_SOURCE_UNAVAILABLE`.** Select if rules 1–4 cannot be established because the receipt timestamp, acknowledgement-authority state, checkpoint completeness, transaction outcome, or writer fence is unavailable or untrustworthy. An incomplete history is never proof that an attempt or commit did not occur. If the overall operation outcome cannot be reconciled, effective lifecycle is `UNRESOLVED`, the reader is `HALTED`, the committed reservation is retained, and no content may be released or replayed. Preserve a separate higher-priority internal ledger result in `expected_internal_code`.

**Contradictory success records:** if a purported success row has `ack_received_at >= trusted_commit_time`, it cannot be accepted as `DELIVERED`. If `ack_received_at >= Tack`, rule 1(a) selects `ACK_TIMED_OUT`; if it is before `Tack` but not strictly before the purported commit time, use `ACK_SOURCE_UNAVAILABLE` for acknowledgement status and `LEDGER_INTEGRITY_UNPROVEN` internally unless rule 1 independently established timeout. In either case, effective operation lifecycle is `UNRESOLVED`, reader `HALTED`, reservation retained, no delivery claim, and no replay. A purported success row timestamped at/after `Tack`, without a proven late receipt or journaled deadline rejection, is not sufficient by itself to classify the acknowledgement as timed out; use `ACK_SOURCE_UNAVAILABLE` plus `LEDGER_INTEGRITY_UNPROVEN`.

This ordered rule is intentionally disjoint for the named cases:
- a pre-deadline receipt with an in-progress attempt selects `WAITING`;
- a pre-deadline receipt whose attempt is proven closed without commit selects `ACK_COMMIT_FAILED`, even when observed after `Tack`;
- no receipt by the deadline, positively proven by the complete ingress/outcome watermarks, selects `ACK_TIMED_OUT`;
- a journaled deadline rejection selects `ACK_TIMED_OUT`;
- uncertain evidence selects `ACK_SOURCE_UNAVAILABLE`, unless independently sufficient timeout evidence already selected rule 1.

Existing handling of `ACK_INVALID`, `ACK_MISMATCH`, and `ACK_REPLAYED` remains in force. A second receipt cannot create a second commit opportunity; its event result is addressed in §3.

## 2. C16-S2 — Separate checkpoint completeness from terminal recovery closure

Entry 289 §2.4 is replaced with two separate evidence predicates:

**`checkpoint_complete`** is true only when the ledger authority returns an authenticated checkpoint identity and monotonically increasing sequence/watermark; records are contiguous and gap-free through that watermark; the transaction outcome index has been queried for every registered attempt through it; and ledger/anchor integrity is verified. A current attempt may be `IN_PROGRESS`. A live writer may still be capable of committing. Therefore this predicate can support observation of a waiting operation, but it cannot prove recovery closure or that no attempt remains in flight.

**`recovery_closed`** requires `checkpoint_complete` plus: every registered attempt has an authenticated terminal result or recovery closure; the transaction outcome index proves whether the acknowledgement/`DELIVERED` row committed; and an authenticated writer-fence acknowledgement establishes that no previous writer can still commit. In-progress attempts and unfenced writers are incompatible with `recovery_closed`.

Use these predicates by class:
- `WAITING` before `Tack` requires a current `checkpoint_complete`; the operation may contain one live `IN_PROGRESS` attempt. Do not require terminal closure for an honest in-progress status.
- `ACK_COMMIT_FAILED` requires `recovery_closed` and positive proof that no success committed.
- Timeout due to a missing receipt requires an acknowledgement-ingress watermark proving receipt history through `Tack`, plus `recovery_closed` and a complete transaction outcome index proving no success by the deadline.
- `ACK_TIMED_OUT` from a journaled deadline rejection requires the authenticated complete attempt/outcome evidence for that rejection.
- If checkpoint completeness, the required deadline watermark, transaction index, or writer fence is missing for a classification that depends on it, use `ACK_SOURCE_UNAVAILABLE`, unless independent evidence already satisfies the timeout rule.

A58 is the checkpoint-versus-closure discriminator: the authenticated checkpoint and current outcome index are complete through their watermark, the unique attempt is explicitly `IN_PROGRESS`, the writer is live, and the evaluation time is `Tack−2s`. It expects `WAITING`; it does not claim `recovery_closed`. With a truncated watermark, the same setup expects `ACK_SOURCE_UNAVAILABLE`. With the attempt terminally rolled back and recovery closure complete, it expects `ACK_COMMIT_FAILED`.

## 3. C16-S3 — One acknowledgement commit opportunity per operation/handoff, not per receipt

Replace Entry 289 §2.2's “for that receipt” language:

There is at most one acknowledgement/`DELIVERED` commit opportunity per `(operation_id, handoff_id)`, regardless of how many receipt event IDs or signed receipt envelopes the authority sends. The first authenticated eligible receipt consumes the operation-bound one-shot slot when its attempt is durably registered. Once an attempt is registered, no second attempt may be registered after success, rollback, abort, interruption, deadline rejection, or recovery closure. Neither the live coordinator nor recovery may restart it, including before `Tack`.

Any subsequent receipt for the same operation/handoff after the one-shot slot has been consumed is audited as ineligible with `ACK_REPLAYED`, even if it has a different event ID. The audit preserves the original receipt/event identity and must not overwrite the first attempt's durable result. A later receipt cannot change `ACK_COMMIT_FAILED` back to pending or create a new route to `ACK_ACCEPTED`.

**A63** is the discriminating fixture: receipt E1 is authenticated before `Tack`, attempt 1 is durably registered and rolls back, and a distinct validly signed event E2 for the same operation/handoff arrives before `Tack`. Expected event result `ACK_REPLAYED`; the operation's effective state remains `UNRESOLVED` / reader `HALTED` / reservation retained, with exactly one registered commit attempt and zero additional writer calls. A duplicate event ID remains rejected under the existing replay rule.

## 4. C16 clock-boundary requirement — Uncertain time mapping rejects before success

The clock relation in Entry 289 §2.4 is a pre-commit safety condition, not merely a post-commit classification rule. The coordinator/ledger mapping must provide a bounded uncertainty interval for the actual atomic linearization time in the coordinator's protected monotonic domain. A successful acknowledgement/`DELIVERED` commit is permitted only if the *latest possible* linearization time under that interval is strictly less than `Tack`. If the interval touches or crosses `Tack`, abort the transaction before either success row is made durable and record a non-successful clock/deadline abort in the authoritative journal. Do not commit on a best-case timestamp and later relabel delivery as unavailable.

Where the interval crosses the deadline and no independent local receipt/deadline evidence proves that the acknowledgement was actually late, report `ACK_SOURCE_UNAVAILABLE` / effective `UNRESOLVED`, halt new content-bearing operations, retain reservation, and do not replay. If a trusted local receipt was already at/after `Tack` or a complete journal proves the deadline rejection at/after `Tack`, rule 1 selects `ACK_TIMED_OUT`. A success row created despite an overlapping uncertainty interval is `LEDGER_INTEGRITY_UNPROVEN`.

Discriminating test: sample an apparent commit time at `Tack−1ms`, then force the mapped uncertainty upper bound to reach `Tack+2ms`. The transaction must not persist acknowledgement evidence or `DELIVERED`; it records a non-successful abort. Without an independent timeout proof the status is `ACK_SOURCE_UNAVAILABLE`, not `ACK_ACCEPTED`. A second variant with local receipt at `Tack+1ms` is `ACK_TIMED_OUT`.

## 7. C16-S6 — Clock-invalidated nonce precedence has typed controls

Amend Entry 283 §2.1 item 2 narrowly: a correctly authenticated, correctly challenge-bound attestation is also `APPROVAL_LATE` when received after that same pending nonce has already been invalidated by recognized clock-safety failure (unknown/unavailable suspend semantics or a detected backward wall-clock step), even if its receipt precedes the nominal challenge deadline. For this exception, internal result is `DECISION_EXPIRED`, issuance result `APPROVAL_LATE`, and Owner-channel result `OWNER_ATTESTATION_LATE`. The nonce cannot issue or revive a decision.

This exception applies only after successful authentication and exact binding checks. An invalid signature, replayed event, identity mismatch, or wrong nonce continues to yield `OWNER_ATTESTATION_INVALID` / `APPROVAL_CHANNEL_UNTRUSTED` under Entry 283 §2.1 item 1, even if clock-safety invalidation has already occurred. The first correctly authenticated presentation for a clock-invalidated nonce is classified `APPROVAL_LATE`; any re-presentation of the same consumed event is a replay and must not change the initial audit result. No attestation by the endpoint remains `OWNER_NO_RESPONSE` / internal `NONE`.

Typed fixtures A64–A68 exercise:
- A64: invalid signature after clock-safety nonce invalidation, at `T0+40s`;
- A65: correctly signed attestation bound to a different nonce after invalidation;
- A66: a clock-invalidated nonce's event already received once, then the same event ID is replayed;
- A67: no attestation is received by the fixed endpoint;
- A68: nominal late attestation at `T0+121s` with no clock-safety event.

A64–A66 must retain the invalid-attestation tuple and must not disclose nonce status to the requester during the fixed window; A67 is `OWNER_NO_RESPONSE`; A68 is the inherited nominal `APPROVAL_LATE` control. A46/A47 remain the positive controls for correctly authenticated, exactly bound attestations after clock-safety invalidation.
