## 6. V2 / V3 TRUST-BOUNDARY LESSONS PRESERVED

The clean V2 reconstruction and the subsequent V3 audit established several durable distinctions.

### Core distinctions

```text
identity != authority
frozen dataclass != trust boundary
signature generation != signature verification
PID field != OS-observed process identity
lineage != authorization
implementation != validated behavior
```

A central discovery was that the real missing abstraction was not “another validation helper.” It was an authority capable of issuing and verifying trusted credentials/capabilities for invocation.

The earlier V3 implementation then showed how easy it was to create security scaffolding that looked complete while remaining semantically unenforced:

- signatures were calculated but not always actually verified;
- DACL concepts existed without full OS enforcement;
- `get_client_pid()` could fail and permit a fail-open path;
- identity could be accepted from generation/equality rather than proof of authority issuance;
- invalid identity could degrade to `None` and still allow persistence;
- learning provenance was contractual rather than actually connected.

### Durable methodological lesson

Never infer a security property from the mere presence of code bearing the right names.

Always ask:

```text
What exact branch reaches the enforcement?
What trusted input enters it?
What happens on invalid input?
What persists after rejection?
Can the test reach the critical code?
```

## 7. AUTHORITY CONTRACT RECONSTRUCTION

After repeated V4 findings, the conversation crystallized the difference between identity and invocation authorization.

The proposed minimal authority abstraction was an invocation capability with fields such as:

- issuer PID;
- authorized consumer PID;
- capability ID;
- invocation ID;
- scope;
- issued-at;
- expires-at;
- signature.

The trust chain became:

```text
TRUST ANCHOR
→ AUTHORITY
→ ISSUER
→ CONSUMER
→ VERIFIER
```

with a security contract:

```text
OS-observed client identity
→ authorized consumer verification
→ capability validation
→ capability consumption
→ invocation acceptance
```

SelfAudit was required to receive a validated invocation context rather than caller-asserted identity, and single-use behavior had to be interprocess-atomic rather than protected only by a local dictionary.

This led to the V5 implementation direction:

- `InvocationCapability`
- `CapabilityIssuer`
- `CapabilityVerifier`
- `CapabilityRegistry`
- fail-closed `SelfAuditService`
- OS-observed client PID at the IPC trust boundary

## 8. V5 RE-AUDIT AND THE SECOND-LAYER VERIFICATION FAILURE

The V5 implementation was published to the GitHub PR/branch history, but Codex identified five important blockers:

### V5-01
SelfAudit could still be given a fabricable context; validation covered structure rather than proving that a capability had actually been issued and consumed by the authority.

### V5-02
The registry used `fcntl`, which was incompatible with Windows.

### V5-03
Verification and consumption were not truly atomic and were exposed to a TOCTOU race.

### V5-04
`CapabilityIssuer` was not anchored to `RootTrustAnchor`.

### V5-05
Execution binding was incomplete.

The V5R1 remediation then introduced stronger structures:

- frozen `ValidatedInvocationContext`;
- Windows locking using `msvcrt.locking` / `ctypes` fallback;
- `consume_if_valid()` atomic operation;
- RootTrustAnchor binding;
- complete identity binding through the validated context.

The lesson from this round was the same at a deeper level: adding another object or field does not establish trust unless there is a non-fabricable path from authority issuance to consumption to persisted evidence.

## 10. F10 — DATABASE AUTHORITY UNIFICATION

The F10 problem was the presence of separate challenge state that could diverge from join authorization state.

The corrective implementation consolidated both:

```text
join_authorizations
+
challenges
```

into the same authoritative SQLite store and transaction boundary.

Remote code evidence confirms the `challenges` table includes:

- `challenge_id`
- `join_id`
- `challenge`
- `generation`
- `execution_id`
- `issued_at`
- `expires_at`
- `consumed`
- `consumed_at`
- uniqueness on `(join_id, challenge)`
- foreign key to `join_authorizations`

and a separate `CHALLENGE_AUTH_DB` constant remains only as a dead constant rather than an active `sqlite3.connect()` authority.

`REDEEM_JOIN` uses one connection and the same transaction to:

```text
UPDATE join_authorizations
→ UPDATE challenges
→ COMMIT
```

with rollback on failure.

This is a real structural correction. It is not merely documentation.

## 12. CLAUDE F10 RE-AUDIT — F11 DISCOVERY

Claude independently re-audited the remote F10 commit and confirmed F10 itself was correct by code inspection.

However, the re-audit discovered that the test suite did not actually execute the critical redeem-success path.

The reported 23/23 tests were therefore insufficient evidence for:

- exactly-once redeem;
- replay rejection;
- concurrent redeem protection;
- transaction atomicity.

The critical observation was that tests used invalid placeholder values such as:

```text
dummy_signature
dummy_signature_for_test
test_key
```

which caused execution to fail before the real verification/consumption code ran.

Coverage showed the important redeem region remained unexecuted.

### F11 root finding

The tests were not simply weak assertions. They were exercising the wrong branch.

This produces the stronger methodological rule:

> A test can execute, assert something meaningful and pass, yet still provide zero evidence for the security property claimed if the test exits before the property under test is reached.

This is one of the most important audit lessons in this conversation.

## 13. F11 TEST EVIDENCE GAP — DETAILED LESSONS

Claude classified the missing evidence as:

`F11 = CRITICAL`

because the actual path:

```text
valid join
→ valid challenge
→ valid Ed25519 proof
→ successful redeem
→ atomic consumption
```

had never been demonstrated.

The intended evidence is:

```text
REQUEST_JOIN
→ REQUEST_CHALLENGE
→ stored challenge
→ Ed25519 sign
→ REDEEM_JOIN
→ verify_signature()
→ UPDATE join_authorizations
→ UPDATE challenges
→ COMMIT
→ success=True
```

Then:

```text
second redeem
→ FAIL because consumed
```

and replay/concurrency must operate on a credential that was already valid enough to succeed once.

### Reusable audit guardrail

Do not treat:

```text
SUCCESS != observed

```

but instead prove the exact semantic transition.

For exactly-once, the first operation must succeed.

For replay protection, the original credential must first be valid.

For atomic rollback, failure must occur between the two writes, not before the first write.

For concurrency, two consumers must actually race on the same valid state; two sequential failures do not demonstrate race safety.

## 14. HMAC VS ED25519 — CRYPTOGRAPHIC CONTRACT CLARIFICATION

A significant clarification was required because `authority_service.py` contains an HMAC helper:

```text
_sign_data()
_verify_signature()
```

while `REDEEM_JOIN` uses:

```text
ed25519_verify_signature(public_key, challenge_bytes, signature_bytes)
```

The repository also contains:

`iabv_v15.services.phase3.ed25519_keys`

which provides the existing Ed25519 implementation.

Therefore the correct interpretation is:

```text
Phase 2 HMAC
≠
Phase 3 proof-of-possession Ed25519
```

The F11 tests must use the existing Ed25519 implementation and must not switch to HMAC merely to obtain passing tests.

This distinction is important because using HMAC in the F11 fixture would hide an integration defect instead of testing the intended Phase 3 protocol.

The required future test flow is:

```text
real Ed25519 keypair
→ REQUEST_JOIN stores public key
→ REQUEST_CHALLENGE stores real nonce
→ sign exact stored nonce
→ encode signature correctly
→ REDEEM_JOIN
→ Ed25519 verification
```

The implementation should reuse the existing Ed25519 functions rather than introduce another cryptographic subsystem.

```text

test pass != objective satisfaction
runtime completion != semantic progress
```

```text

→ replay behavior
```

### Test quality

Every important security test should identify:

```text
PRECONDITION
→ ACTION
→ EXACT ENFORCEMENT POINT
→ EXPECTED FAILURE/SUCCESS
→ OBJECTIVE-LEVEL ASSERTION
```

### Causal integrity

Do not infer causality from temporal sequence alone.

### Minimal discriminating test

Prefer one test that distinguishes two plausible explanations over a large number of tests that all exercise the same trivial error branch.
