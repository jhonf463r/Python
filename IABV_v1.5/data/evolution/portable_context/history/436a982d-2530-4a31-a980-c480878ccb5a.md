VISIÓN CENTRAL:
El sistema debe tener un meta-modelo operativo del entorno y de sí mismo.
No solo saber qué herramientas existen en teoría.
Sino ver en tiempo real:
- qué está abierto en la pantalla
- qué está haciendo cada ventana
- qué está pasando en segundo plano
- si hay internet y qué calidad tiene
- si Codex tiene el hilo correcto activo
- si Codex tiene mensajes disponibles o están agotados
- si hay un ciclo infinito, bloqueo, throttling o bug activo
- qué consume RAM, CPU y GPU ahora mismo
- qué está bloqueando una tarea antes de intentarla
Y usar todo eso para razonar mejor, deducir lo que está pasando,
proponer soluciones y aprender de cada interacción.

TRES CAPAS QUE DEBES CERRAR:

CAPA 1 — OBSERVABILIDAD MULTIMODAL ACTIVA
El sistema debe observar continuamente:

Ventanas abiertas:
- qué programas están corriendo
- qué ventana está en foco
- qué título tiene cada ventana relevante
- si Codex está abierto y en qué hilo
- si ChatGPT está abierto y en qué conversación
- si el hilo activo es el correcto para la tarea

Estado de herramientas externas antes de usarlas:
- si Codex tiene mensajes disponibles o están agotados
- si ChatGPT tiene sesión activa o expirada
- si Claude tiene créditos disponibles
- si Ollama está respondiendo en este momento
- si hay un bloqueo de IP, rate limit o cuota activa

Estado de red:
- si hay conexión a internet
- calidad aproximada de la conexión
- si un servicio externo está caído o lento
- si el problema es red vs herramienta vs código

Estado del sistema en segundo plano:
- procesos que consumen recursos excesivos
- ciclos infinitos o procesos colgados detectables
- apps que interfieren con la captura o el foco
- cambios relevantes desde el último ciclo

CAPA 2 — WORLD MODEL OPERATIVO
Con todo lo observado, el sistema debe construir y mantener un modelo
vivo del mundo en el que opera:

WorldModelSnapshot debe contener:
- active_windows: ventanas abiertas y su estado
- focused_window: qué tiene el foco ahora
- tool_live_status: estado vivo de cada herramienta
  - ollama: disponible/no disponible/lento
  - codex: abierto/cerrado/hilo correcto/mensajes disponibles/agotados
  - chatgpt: sesión activa/expirada/bloqueada
  - claude: disponible/limitado/bloqueado
- network_status: conectado/desconectado/lento/bloqueado
- background_processes: procesos relevantes en segundo plano
- detected_blocks: qué está bloqueando qué tarea
- inferred_state: qué deduce el sistema de todo lo anterior
- confidence: qué tan confiable es esta observación
- last_updated: cuándo se actualizó por última vez

Este modelo debe:
- actualizarse en segundo plano sin bloquear el chat
- alimentar al PerceptionSnapshot junto con EnvironmentSelfModel
- ser consultado por el orquestador antes de decidir qué ruta usar
- ser consultado antes de intentar cualquier herramienta externa
- nunca ser modificado por la UI, solo leído

CAPA 3 — SELF-MODEL OPERATIVO CON RAZONAMIENTO DEDUCTIVO
El sistema debe saber no solo qué tiene, sino qué puede hacer ahora mismo
y por qué algo no está funcionando.

Cuando detecta un problema debe razonar así:
- "Codex está abierto pero el hilo activo no es el de IABV"
  → no intentes pegar ahí, abre el hilo correcto primero
- "Codex está abierto pero no quedan mensajes disponibles"
  → notifica al usuario antes de intentar la consulta
- "ChatGPT muestra Just a moment..."
  → hay verificación de seguridad activa, no es selector roto
- "La red está disponible pero el servicio externo no responde"
  → el problema es el servicio, no la conexión
- "Hay un proceso consumiendo el 80% de CPU"
  → avisa antes de lanzar una tarea pesada
- "El foco está en otra ventana"
  → espera o pide permiso antes de interactuar

Este razonamiento deductivo debe:
- entrar al DecisionContext antes de cada decisión
- bloquear rutas que no pueden funcionar en el estado actual
- sugerir la alternativa más útil disponible
- registrar el aprendizaje para no repetir el mismo error

INTEGRACIÓN CON LO QUE YA EXISTE:
- WorldModelSnapshot entra a PerceptionSnapshot como world_model
- No reemplaza EnvironmentSelfModel ni UniversalPerceptionSignal
- Los tres se complementan:
  EnvironmentSelfModel = conocimiento del cuerpo hardware/runtime
  UniversalPerceptionSignal = observación de un programa o página específica
  WorldModelSnapshot = panorama completo del mundo operativo en tiempo real
- AdaptiveTaskOrchestrator consulta world_model antes de decidir ruta
- AutonomyGovernancePolicy usa world_model para bloquear rutas inviables
- El chat puede responder preguntas como "qué está pasando?" desde world_model
- EvolutionCenter muestra world_model como observador, sin decidir

PERMISOS Y TRANSPARENCIA:
Si el sistema necesita observar algo que requiere permiso del usuario
debe pedirlo explícitamente en lenguaje simple:
"Para saber si Codex tiene mensajes disponibles necesito observar
esa ventana. ¿Me das permiso?"

Nunca debe:
- asumir que tiene permiso para observar todo
- actuar sobre una ventana sin confirmación
- fingir que observó algo que no pudo leer
- marcar como disponible una herramienta que no verificó

CASOS QUE DEBE RESOLVER CORRECTAMENTE:
1. Usuario pide consultar Codex pero Codex no tiene mensajes
   → el sistema lo detecta antes de intentarlo y lo notifica
2. Usuario pide consultar Codex pero el hilo activo es el chat
   personal del usuario, no el hilo de IABV
   → el sistema lo detecta y no pega en ese hilo
3. ChatGPT muestra verificación de seguridad
   → el sistema lo detecta como browser_security_verification
   y no lo trata como selector roto
4. Usuario pregunta "qué está pasando con mi internet?"
   → el sistema responde desde network_status con evidencia real
5. Usuario pregunta "por qué no responde Codex?"
   → el sistema responde desde world_model con el estado real
6. Hay un proceso en segundo plano consumiendo muchos recursos
   → el sistema lo menciona si afecta la tarea actual
7. Usuario pregunta "qué tienes abierto ahora?"
   → el sistema responde desde active_windows con lo real
